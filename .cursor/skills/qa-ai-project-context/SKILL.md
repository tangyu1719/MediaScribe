# 测开岗位 AI 提效 · 项目上下文建设

## 何时使用

- 用户要在**真实项目**中用 AI 辅助测试，但输出太泛、不符合业务。
- 用户要建设/维护**项目上下文资产**（术语、流程、规则、历史缺陷）。
- 用户要设计测试类 **Skill**（需求梳理、缺陷描述、回归分析、产品学习）。
- 当前项目涉及 **SHARE3DCAM / SHARE PointClouds Studio** 或类似「采集→重建→CAD→检查」链路。

## 核心原则（必须遵守）

1. **AI 不是替代经验，而是放大经验** — 没有上下文，AI 只能产出通用测试点。
2. **Skill ≠ 单段 Prompt** — Skill = 固定规则 + 项目上下文 + 输入输出规格 + 经验库 + 闭环验证。
3. **禁止编造业务** — 术语、流程、规则须来自用户提供的上下文资产或代码/文档；缺失时标注「待补充」。
4. **测开岗位价值** — 核心竞争力是把隐性业务知识转化为 AI 可复用的结构化资产。

## 执行流程

### Step 1：确认上下文资产是否齐全

对照 [reference.md](reference.md) 第四节表格，检查是否已有：

| 类型 | 最低要求 |
|------|----------|
| 产品建模 | 定位、用户、目标 |
| 核心流程 | 端到端链路（采集→导入→重建→CAD→检查） |
| 专业术语 | 点云、3DGS、GNSS、控制点、图层等定义 |
| 业务规则 | 重建约束、设备适配、参数限制 |
| 测试经验 | 高频风险点、典型异常 |
| 历史单据 | 缺陷现象、复现、影响范围 |
| 测试规范 | 用例/Bug/报告模板 |

缺项时先引导用户补齐，**不得用通用模板冒充项目知识**。

### Step 2：选择并执行对应 Skill

按任务类型选用下列 Skill 模板（输入/上下文/输出定义见 reference 第五节）：

| Skill | 触发场景 |
|-------|----------|
| 需求梳理测试点 | 新需求、原型、手册 → 测试范围与用例 |
| 缺陷描述优化 | 截图/步骤/结果 → 规范 Bug 单 |
| 版本回归分析 | 版本变更说明 → 回归范围与优先级 |
| 产品学习助手 | 不懂的概念/功能 → 解释 + 测试关注点 |

输出时必须引用已提供的上下文片段；无法引用时说明依据不足。

### Step 3：三阶段落地检查

1. **先理解产品** — 术语词库、端侧关系、流程图、待确认问题清单。
2. **整理测试上下文** — 节点 I/O、易错步骤、典型数据、Bug 根因与临时解法。
3. **喂给 AI 使用** — 基于真实资料生成用例、计划、Bug 描述、回归脚本、学习笔记。

### Step 4：个人文档清单（可执行交付）

帮助用户建立或更新以下五份文档（见 reference 第九节）：

1. 产品业务流程逻辑
2. 专业术语与功能关系说明
3. 核心流程测试点清单
4. Bug 与回归经验库
5. AI 辅助测试 Prompt / Skill 库

## 输出格式

```markdown
## 任务类型
（需求梳理 / 缺陷优化 / 回归分析 / 产品学习 / 上下文建设）

## 引用的上下文资产
- [列出实际引用的术语、流程、规则条目]

## 主要输出
（测试范围、Bug 单、回归清单、概念解释等）

## 待补充上下文
- [缺失且影响质量的条目]

## 建议沉淀
- [本次应写入项目上下文库的新知识]
```
